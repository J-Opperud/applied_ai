You can build the most feature-rich API in the world, but if it's insecure, none of that matters. Security isn't something you bolt on at the end — it's something you build in from the start. This lesson covers the essential security practices every API developer needs to know.


Think of API security like home security. A front door lock (authentication — you just built this) is necessary but not sufficient. You also need to think about who can approach your house (CORS), how many times someone can ring the doorbell before it's suspicious (rate limiting), and whether someone could slip a lockpick through the mail slot (injection attacks).
CORS — Cross-Origin Resource Sharing

When your Streamlit frontend (running on localhost:8501) tries to call your FastAPI backend (running on localhost:8000), the browser blocks it by default. This is a security feature called the Same-Origin Policy: browsers prevent JavaScript from making requests to a different origin (domain, port, or protocol) than the one that served the page.

CORS tells the browser which origins are allowed to make requests to your API.
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "<http://localhost:8501>",       # Your Streamlit app
        "<http://localhost:3000>",       # A React frontend (if you have one)
    ],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

In development, you might allow all origins (allow_origins=["*"]). In production, always list specific origins.
SQL Injection Prevention

SQL injection is one of the most common and dangerous web vulnerabilities. An attacker inserts malicious SQL into your application's queries:
# ❌ DANGEROUS — raw SQL with string formatting
@app.get("/users")
def search_users(name: str, db: Session = Depends(get_db)):
    result = db.execute(f"SELECT * FROM users WHERE name = '{name}'")
    return result.fetchall()

An attacker could send name='; DROP TABLE users; -- and delete your entire database.

The fix: never use string formatting for SQL. Use the ORM:
# ✅ SAFE — SQLAlchemy ORM (what you've been doing all along)
@app.get("/users")
def search_users(name: str, db: Session = Depends(get_db)):
    users = db.query(User).filter(User.name == name).all()
    return users

SQLAlchemy automatically parameterizes the query. The user's input is treated as data, never as SQL code.


If you must use raw SQL (rare), always use parameterized queries:
# ✅ SAFE — parameterized raw SQL
from sqlalchemy import text
result = db.execute(text("SELECT * FROM users WHERE name = :name"), {"name": name})

Reading Files

The open() function opens a file. Always use it inside a with block, which automatically closes the file when you're done:
# Read the entire file as one string
with open("notes.txt", "r") as file:
    content = file.read()
    print(content)

# Read line by line
with open("notes.txt", "r") as file:
    for line in file:
        print(line.strip())    # .strip() removes the trailing newline

# Read all lines into a list
with open("notes.txt", "r") as file:
    lines = file.readlines()    # Each line is an element in the list

The "r" stands for "read mode." This is the default, so open("notes.txt") works too, but being explicit is clearer.
Writing Files
# Write mode ("w") — creates file or OVERWRITES existing content
with open("output.txt", "w") as file:
    file.write("First line\\n")
    file.write("Second line\\n")

# Append mode ("a") — adds to the end without overwriting
with open("output.txt", "a") as file:
    file.write("Third line (appended)\\n")

Critical warning: Write mode ("w") erases everything in the file before writing. If the file has important data and you use "w" instead of "a", that data is gone. There is no undo.
Why with Matters

The with statement ensures the file is properly closed even if an error occurs. Without it:
# Risky — if an error occurs between open() and close(), the file stays open
file = open("data.txt", "r")
content = file.read()
file.close()

# Safe — the file is guaranteed to close
with open("data.txt", "r") as file:
    content = file.read()
# File is automatically closed here

Always use with. There is no good reason not to.

Faster Programing

in Module 1, you learned what AI is and why it matters. Now we shift gears. For the rest of this course, you’re learning to build, and building well means writing code that doesn’t just work, but works efficiently.

Here’s a scenario. You write a Python script that processes a list of 100 customer records. It runs in half a second. Great. Your boss says, “This works, let’s run it on our full database.” The full database has 10 million records. Your script now takes 14 hours. Same code, same logic, it just doesn’t scale.

This is the problem Big O notation solves. It gives you a way to predict how your code will behave as the input gets larger, before you run it on 10 million records and wait all day.
What Big O Actually Measures

Big O notation describes the relationship between the size of the input and the number of operations your code performs. It doesn’t tell you the exact time in seconds, that depends on your computer’s speed, what else is running, and a dozen other factors. Instead, it tells you the growth rate. How does the work increase as the data increases?
image-1f6d8a85-523c-4175-97bf-5d4a4e6841a1.png.jpeg

Think of it like describing a road trip. You wouldn’t say “the trip takes exactly 3 hours and 42 minutes”, that depends on traffic, speed limits, and bathroom breaks. But you can say “the trip is proportional to the distance.” Drive twice as far, it takes roughly twice as long. That “proportional to distance” is the Big O of your road trip: O(distance).

In code, “distance” becomes “the size of the input,” and we call it n.
The Four Complexities You Need to Know

There are many Big O classifications, but four cover the vast majority of code you’ll encounter:
O(1) - Constant Time: “It doesn’t matter how big the input is.”

The operation takes the same amount of time regardless of input size. Accessing an item in a list by index is O(1):
my_list = [10, 20, 30, 40, 50]
value = my_list[3]  # Always one operation, whether the list has 5 or 5 million items

It doesn’t matter if the list has 5 elements or 5 million. Grabbing item #3 is one operation. Looking up a key in a dictionary is also O(1).
O(n) - Linear Time: “Double the input, double the work.”

The operation scales directly with the input size. Looping through a list is the classic example:
def find_item(items, target):
    for item in items:       # One pass through the list
        if item == target:
            return True
    return False

If the list has 100 items, you might check up to 100 items. If it has 10,000 items, you might check up to 10,000 items. The work grows linearly with the input.
O(n²) - Quadratic Time: “Double the input, quadruple the work.”

This usually happens with nested loops, a loop inside a loop:
def find_duplicates(items):
    duplicates = []
    for i in range(len(items)):           # Outer loop: n times
        for j in range(i + 1, len(items)):  # Inner loop: up to n times each
            if items[i] == items[j]:
                duplicates.append(items[i])
    return duplicates

For every item in the list, you’re comparing it against every other item. With 100 items, that’s roughly 100 × 100 = 10,000 comparisons. With 10,000 items, that’s 10,000 × 10,000 = 100,000,000 comparisons. This is where code starts to feel slow.
O(log n) - Logarithmic Time: “Double the input, add one step.”

This is the efficiency sweet spot. Binary search is the classic example, you cut the search space in half with each step:
def binary_search(sorted_list, target):
    low, high = 0, len(sorted_list) - 1
    while low <= high:
        mid = (low + high) // 2
        if sorted_list[mid] == target:
            return mid
        elif sorted_list[mid] < target:
            low = mid + 1       # Ignore the left half
        else:
            high = mid - 1      # Ignore the right half
    return -1

A sorted list of 1,000 items? Binary search finds any item in at most 10 steps. A sorted list of 1,000,000 items? At most 20 steps. That’s the power of logarithmic growth, doubling the input only adds one more step.
Why This Matters for AI Engineering

You might be thinking: “I’m here to learn AI, not algorithms.” Here’s why this matters for you specifically:

When you build AI applications (Modules 7-8), you’ll work with thousands or millions of documents stored in vector databases. The difference between O(n) search (check every document) and O(log n) search (use an index) is the difference between a chatbot that responds in 50 milliseconds and one that takes 30 seconds. Your users won’t wait.

When you process data with pandas (later this module), understanding why some operations are fast (vectorized operations — essentially O(n)) and some are slow (row-by-row loops — often O(n²)) will save you hours of debugging slow pipelines.

Big O isn’t abstract theory. It’s the reason your code will or won’t work in production.

approach 1: Nested Loops - O(n²)
def has_duplicate_nested(data):
    """Compare every element to every other element."""
    for i in range(len(data)):
        for j in range(i + 1, len(data)):
            if data[i] == data[j]:
                return True
    return False

This checks every possible pair. For a list of 1,000 items, that’s up to ~500,000 comparisons. For 10,000 items, it’s up to ~50,000,000.
Approach 2: Sort First - O(n log n)
def has_duplicate_sort(data):
    """Sort the list, then check adjacent elements."""
    sorted_data = sorted(data)          # O(n log n) — Python's sort
    for i in range(len(sorted_data) - 1):
        if sorted_data[i] == sorted_data[i + 1]:  # O(n) — one pass
            return True
    return False

Sorting is O(n log n), and then one linear scan is O(n). Total: O(n log n). Much better than O(n²).
Approach 3: Use a Set - O(n)
def has_duplicate_set(data):
    """Add elements to a set; if we try to add one that's already there, it's a duplicate."""
    seen = set()
    for item in data:           # One pass through the data: O(n)
        if item in seen:        # Set lookup: O(1)
            return True
        seen.add(item)          # Set insertion: O(1)
    return False

One loop, and each set operation is O(1). Total: O(n).
Let’s Time Them
import time
import random

def benchmark(func, data):
    """Time how long a function takes to run."""
    start = time.time()
    result = func(data)
    end = time.time()
    return end - start

# Generate test data with no duplicates (worst case — must check everything)
sizes = [1000, 5000, 10000, 20000]

for size in sizes:
    data = list(range(size))        # No duplicates — forces full scan
    random.shuffle(data)            # Randomize order

    t1 = benchmark(has_duplicate_nested, data)
    t2 = benchmark(has_duplicate_sort, data)
    t3 = benchmark(has_duplicate_set, data)

    print(f"n={size:>6}  |  Nested: {t1:.4f}s  |  Sort: {t2:.4f}s  |  Set: {t3:.4f}s")

Notice the pattern:

    Nested (O(n²)): When n doubles from 10,000 to 20,000, the time roughly quadruples. This is the signature of quadratic growth.
    Sort (O(n log n)): When n doubles, the time slightly more than doubles. Fast enough for most purposes.
    Set (O(n)): When n doubles, the time roughly doubles. The fastest approach.

The takeaway: All three functions produce the correct answer. The difference is entirely in how they scale. At n=1,000, you might not notice. At n=20,000, the nested approach is 5,000x slower than the set approach. At n=1,000,000 (common in real data), the nested approach would take hours while the set approach takes milliseconds.

Step 1: Your Browser Looks Up the Address (DNS)

Your browser doesn't actually know where "google.com" lives. Domain names like "google.com" are for humans - computers communicate using IP addresses, which are numerical identifiers like 142.250.80.46.

So the very first thing your browser does is ask: "What's the IP address for google.com?" It sends this question to a DNS server (Domain Name System). Think of DNS as the internet's phone book - you give it a name, it gives you a number.


image (7).png


Your computer usually knows which DNS server to ask because your internet provider (or your Wi-Fi router) configured it automatically. The DNS server looks up the name and responds with the IP address. This usually takes milliseconds.
Step 2: Your Browser Connects and Sends a Request (HTTP)

Now that your browser knows the IP address, it connects to that server and sends an HTTP request. You already know about HTTP from Module 4 - it's the protocol (the set of rules) that browsers and servers use to communicate.

The request includes several pieces of information: the method (GET - because you want to get a page), the path (/ - the root page), headers (metadata like what browser you're using, what language you prefer, and whether you accept compressed data), and sometimes a body (not for GET requests, but for POST requests when you're sending data).

This is the exact same structure you worked with when building API endpoints in FastAPI. The web isn't using some different system for websites versus APIs - it's all HTTP, all the way down.
Step 3: The Server Responds

Google's server receives your request, processes it (figures out what page to show you), and sends back an HTTP response. This response contains a status code (200 OK - success), headers (content type, cache rules, security settings), and a body (the actual HTML, CSS, and JavaScript that make up the page).

You remember status codes from Module 4:

    200 - Everything worked
    301 - This page moved permanently (the server tells your browser the new address)
    404 - Not found (the thing you asked for doesn't exist)
    500 - Server error (something broke on their end)

These codes aren't just API concepts. Every single webpage you've ever loaded returned one of these codes. Your browser just handles them silently - redirecting on 301s, showing error pages on 404s.
Step 4: Your Browser Renders the Page

The response body contains three types of content: HTML (the structure - headings, paragraphs, images, links), CSS (the styling - colors, fonts, spacing, layout), and JavaScript (the behavior - what happens when you click a button, type in a search box, or scroll down).

Your browser reads the HTML first to build the structure, applies the CSS to make it look right, then runs the JavaScript to make it interactive. This entire process - from DNS lookup to rendered page - typically takes under a second.


image (8).png
HTTPS: The Secure Version

You probably noticed the "https://" at the start of the URL. The "s" stands for secure. HTTPS encrypts the communication between your browser and the server so that nobody in between (your Wi-Fi provider, a hacker on the same coffee shop network, your ISP) can read the data being exchanged.

For AI applications that handle user data, API keys, or any sensitive information, HTTPS is not optional - it's essential. Every modern browser warns users when a site uses plain HTTP instead of HTTPS.
Why This Matters for AI Engineers

You might be wondering: "I'm building AI applications, not websites. Why do I need to know this?"

Because every AI application has a user interface, and that interface communicates with your backend over HTTP. When you build a Streamlit app in Week 2 that connects to your FastAPI backend, here's what's actually happening: your user's browser loads the Streamlit interface, the interface sends HTTP requests to your FastAPI server, your server processes the request (maybe queries a database, maybe calls an AI model), and the response flows back to the browser to display the result.

Understanding this cycle means you can debug problems. When something doesn't work, you'll know how to check: Is it a DNS issue? A connection problem? A wrong status code? A malformed response? The DevTools Network tab - which you'll use in the Guided Example — makes all of this visible.

You're not just a user of the web anymore. You're a builder. And builders understand their medium.


Last week you learned HTML, CSS, and JavaScript. You built pages, styled them, made them interactive, and connected them to an API. It worked - but it took a lot of code across multiple files in three different languages.

Now imagine you could do all of that in one Python file. No HTML. No CSS. No JavaScript. Just Python.

That’s Streamlit.

Streamlit is a Python library that turns Python scripts into interactive web applications. You write Python, and Streamlit converts it into a fully functional web app with widgets, charts, tables, and layouts - all rendered in the browser.
The Same App, Two Ways

Let’s compare building a simple "Hello World" app:

HTML/CSS/JS version (3 files, ~40 lines):
<!-- index.html -->
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>Hello App</title>
    <link rel="stylesheet" href="styles.css">
</head>
<body>
    <h1>Hello!</h1>
    <input type="text" id="name-input" placeholder="Enter your name">
    <p id="greeting"></p>
    <script>
        document.querySelector("#name-input").addEventListener("input", (e) => {
            document.querySelector("#greeting").textContent = 
                e.target.value ? `Hello, ${e.target.value}!` : "";
        });
    </script>
</body>
</html>

Streamlit version (1 file, 4 lines):
import streamlit as st

st.title("Hello!")
name = st.text_input("Enter your name")
if name:
    st.write(f"Hello, {name}!")

Four lines. One language. No event listeners, no DOM manipulation, no separate CSS file. Streamlit handles all the web rendering for you.
The Re-Run Model (THE Most Important Concept)

Here’s the one thing you absolutely must understand about Streamlit, because everything else builds on it:

Every time a user interacts with any widget, the entire Python script re-runs from top to bottom.

Read that again. It’s not like Flask or FastAPI where specific functions handle specific requests. In Streamlit, the whole script runs again. Every time.

    User types in a text box? Script re-runs.
    User clicks a button? Script re-runs.
    User moves a slider? Script re-runs.

This is radically different from how JavaScript works. In JavaScript, you set up event listeners that run specific functions when specific things happen. In Streamlit, there are no event listeners - the entire script IS the event handler.

This design makes Streamlit incredibly simple to write. But it has one critical consequence:

All variables reset to their initial values on every re-run.

This means code like this does NOT work as a counter:
count = 0  # Resets to 0 every time the script re-runs!
if st.button("Increment"):
    count += 1
st.write(f"Count: {count}")  # Always shows 0 or 1, never 2+

The solution is st.session_state - a dictionary that persists across re-runs. You’ll learn this in the State Management lesson.

Widget Basics: Every Widget Returns a Value

Streamlit widgets aren’t just visual elements - they’re functions that return the current value of the widget:
name = st.text_input("Your name")     # Returns "" until the user types
age = st.slider("Age", 18, 100, 25)   # Returns the current slider value (default 25)
agreed = st.checkbox("I agree")        # Returns True or False
color = st.selectbox("Color", ["Red", "Blue", "Green"])  # Returns the selected option

Because the script re-runs on every interaction, these widgets always return their current value. You can use those values immediately in conditions, calculations, or API calls - no event listeners needed.

This is the power of Streamlit’s model: describe what you want to display, and Streamlit handles the interactivity.

n the last lesson, you learned that Streamlit renders content top-to-bottom - each st.write() or widget appears below the previous one. That works for simple apps, but real dashboards need structure: controls on the side, metrics across the top, content organized into sections.

Think of it like organizing a physical workspace. You could pile everything on one long table. But a well-organized workspace has drawers for tools (sidebar), a quick-reference board at eye level (metrics), and labeled folders for different projects (tabs). Same content, dramatically better experience.

Streamlit has built-in layout components that give you this structure with minimal code.
Page Configuration

Before any content, set the page configuration:
st.set_page_config(

    page_icon="📊",                 # Browser tab icon
    layout="wide",                  # Use full browser width (default is "centered")
    initial_sidebar_state="expanded" # Sidebar starts open
)

This must be the first Streamlit command in your script (after imports). If you call it after any other st. function, you’ll get an error.
Columns: Side-by-Side Content

st.columns() creates horizontal columns. Each column is an independent container:
# Equal-width columns
col1, col2, col3 = st.columns(3)  # 3 equal columns

with col1:
    st.metric("Users", "1,234", "+12%")
with col2:
    st.metric("Revenue", "$45,678", "+8%")
with col3:
    st.metric("Tasks", "89", "-3")

You can also create unequal columns by passing a list of ratios:
left, right = st.columns([2, 1])  # Left is 2x wider than right

The st.metric() component is built for dashboard KPIs - it shows a label, a value, and an optional delta (change indicator) with automatic green/red coloring.
Sidebar: Controls on the Side

The sidebar is perfect for filters, settings, and navigation. Use the st.sidebar prefix:

Or use the with syntax:
with st.sidebar:
    st.title("Controls")
    category = st.selectbox("Category", ["All", "Sales", "Marketing"])

Best practice: put controls (filters, inputs, settings) in the sidebar, and content (charts, tables, data) in the main area. This matches the pattern users expect from dashboards.
Tabs: Organized Sections

Tabs let users switch between different views without scrolling:
tab1, tab2, tab3 = st.tabs(["Overview", "Details", "Raw Data"])

with tab1:
    st.write("High-level summary goes here")
with tab2:
    st.write("Detailed breakdown goes here")
with tab3:
    st.write("Raw data table goes here")

Only one tab is visible at a time. Switching tabs triggers a re-run (like everything else in Streamlit).
Expanders: Show/Hide Content

Expanders collapse content behind a clickable header:
with st.expander("Advanced Settings"):
    threshold = st.slider("Threshold", 0.0, 1.0, 0.5)
    st.write("These settings are hidden by default to keep the UI clean.")

Expanders are great for optional information, detailed explanations, or settings that most users don’t need to see.
Containers

st.container() creates a logical grouping that you can write to out of order:
placeholder = st.container()

# This runs later but appears ABOVE the content below
placeholder.write("This appears at the top!")

st.write("This appears at the bottom")

Containers are useful when you want to reserve a spot in the layout and fill it later (e.g., showing a result above the form that generated it).

Here’s the scenario that confuses every new Streamlit developer. You write this code, expecting a counter that goes up each time you click:
import streamlit as st

count = 0
if st.button("Add one"):
    count += 1
st.write(f"Count: {count}")

You click the button. The count shows 1. You click again. The count… still shows 1. Or sometimes 0. It never reaches 2.

Why? Because of the re-run model. Every time you click the button, the entire script re-runs from the top. Line 3 (count = 0) executes again, resetting your counter to zero before the button logic can increment it.

This isn’t a bug. It’s the fundamental consequence of Streamlit’s design. And the solution is st.session_state.
image (5).png
st.session_state: Memory That Survives Re-Runs

st.session_state is a dictionary that persists across re-runs. It’s like a notebook that Streamlit keeps next to your script - the script can read from it and write to it, and the values stay even when the script re-runs.

Here’s the counter, fixed:
import streamlit as st

# Initialize ONCE — only runs when the key doesn't exist yet
if "count" not in st.session_state:
    st.session_state["count"] = 0

if st.button("Add one"):
    st.session_state["count"] += 1   # Modify the persistent value

st.write(f"Count: {st.session_state['count']}")

Now click the button multiple times. The count goes 1, 2, 3, 4… correctly. The initialization check (if "count" not in st.session_state) ensures we only set the initial value once, on the very first run. Every subsequent re-run skips that line because the key already exists.

This initialization pattern is the most important pattern in Streamlit:
if "key" not in st.session_state:
    st.session_state["key"] = initial_value

You’ll use it for everything: login tokens, form data, chat history, quiz scores, navigation state.
st.form(): Batching Inputs to Prevent Re-Run Overload

Imagine a form with 5 fields. Without st.form(), every time the user changes ANY field, the script re-runs. Filling out 5 fields triggers 5+ re-runs before they even submit.

If each re-run triggers an API call, that’s 5 unnecessary API calls. For expensive operations (AI model calls, database queries), this is wasteful or even rate-limit-triggering.

st.form() solves this by batching inputs:
with st.form("task_form", clear_on_submit=True):
    title = st.text_input("Task title")
    priority = st.selectbox("Priority", ["Low", "Medium", "High"])
    description = st.text_area("Description")

    submitted = st.form_submit_button("Add Task")

    if submitted:
        # This only runs when the submit button is clicked
        st.session_state["tasks"].append({
            "title": title,
            "priority": priority,
            "description": description
        })

Inside a form, widget interactions do NOT trigger re-runs. Only the submit button does. The clear_on_submit=True option resets all fields after submission - perfect for "add item" forms.

Streamlit has widgets for every common input type:

Text: st.text_input(), st.text_area(), st.number_input()

Date/Time: st.date_input(), st.time_input()

Actions: st.button(), st.form_submit_button()

Every widget returns its current value. Inside a form, values are captured when submitted.
Building Multi-Step Flows

Session state enables multi-step experiences. Here’s the pattern for a quiz-style flow:
if "step" not in st.session_state:
    st.session_state["step"] = 1

if st.session_state["step"] == 1:
    st.write("Step 1: Enter your name")
    name = st.text_input("Name")
    if st.button("Next") and name:
        st.session_state["name"] = name
        st.session_state["step"] = 2
        st.rerun()  # Force an immediate re-run to show step 2

elif st.session_state["step"] == 2:
    st.write(f"Welcome, {st.session_state['name']}!")
    st.write("Step 2: Choose your settings")
    # ... more content ...

st.rerun() forces an immediate re-run, which is useful when you change state and want the UI to reflect it without waiting for the user to interact with something.
Common Pitfalls

Pitfall 1: Forgetting initialization. If you read st.session_state["count"] before it exists, you’ll get a KeyError. Always initialize first.

Pitfall 2: Using st.button() for persistent actions. st.button() returns True only during the re-run when it’s clicked. On the next re-run, it’s False again. So code inside if st.button(...) only runs for one run. For persistent changes, store the result in session state.

Pitfall 3: Duplicate widget keys. If you create two widgets with the same label inside a loop, Streamlit can’t tell them apart. Use the key parameter to give each a unique identifier: st.button("Delete", key=f"delete_{item_id}")

et’s build a notes app that demonstrates all the state management patterns you’ll need. Create notes_app.py:
import streamlit as st
from datetime import datetime

st.set_page_config(page_title="Notes App", page_icon="📝", layout="wide")

# --- Initialize Session State ---
if "notes" not in st.session_state:
    st.session_state["notes"] = [
        {"text": "Welcome to the Notes App!", "tag": "General",
         "time": datetime.now().strftime("%H:%M")}
    ]

# --- Sidebar: Tag Filter ---
with st.sidebar:
    st.title("🏷️ Filter by Tag")

    # Get unique tags from all notes
    all_tags = list(set(note["tag"] for note in st.session_state["notes"]))
    all_tags.sort()

    selected_tag = st.radio(
        "Show notes tagged:",
        ["All"] + all_tags
    )

    st.divider()
    st.metric("Total Notes", len(st.session_state["notes"]))

# --- Main Content ---
st.title("📝 Notes App")

# --- Add Note Form ---
with st.form("add_note", clear_on_submit=True):  # Clears fields after submit
    st.subheader("Add a New Note")

    note_text = st.text_area("Note", placeholder="Write your note here...")
    note_tag = st.selectbox("Tag", ["General", "Work", "Personal", "Ideas", "Todo"])

    submitted = st.form_submit_button("➕ Add Note")

    if submitted and note_text.strip():  # Only add if there's actual text
        st.session_state["notes"].append({
            "text": note_text.strip(),
            "tag": note_tag,
            "time": datetime.now().strftime("%H:%M")
        })
        st.rerun()  # Force re-run to show the new note immediately

st.divider()

# --- Display Notes ---
# Filter notes based on sidebar selection
if selected_tag == "All":
    filtered = st.session_state["notes"]
else:
    filtered = [n for n in st.session_state["notes"] if n["tag"] == selected_tag]

st.subheader(f"Notes ({len(filtered)} showing)")

if not filtered:
    st.info("No notes found for this tag. Try 'All' or add a new note!")

# Display each note with a delete button
for i, note in enumerate(filtered):
    col_text, col_delete = st.columns([5, 1])  # 5:1 ratio

    with col_text:
        st.write(f"**[{note['tag']}]** {note['text']}")
        st.caption(f"Added at {note['time']}")

    with col_delete:
        # CRITICAL: unique key for each delete button
        if st.button("🗑️", key=f"delete_{i}_{note['time']}"):
            st.session_state["notes"].remove(note)
            st.rerun()  # Re-run to update the display

    st.divider()

streamlit run notes_app.py

    A form to add notes with a text area, tag selector, and submit button
    The form clears after submission (clear_on_submit=True)
    Notes appear below with their tag and timestamp
    The sidebar lets you filter notes by tag
    Each note has a delete button that removes it

Key Patterns in This Example

Initialization: if "notes" not in st.session_state - the standard pattern.

Form batching: The text area and selectbox inside st.form() don’t trigger re-runs until you click "Add Note."

Unique keys: key=f"delete_{i}_{note['time']}" ensures each delete button is uniquely identified. Without unique keys, Streamlit would confuse which button was clicked.

Tables: st.dataframe() vs st.table()

Streamlit has two ways to display tabular data:

st.dataframe() renders an interactive table. Users can sort columns, resize them, search, and scroll. It handles large datasets efficiently.

st.table() renders a static table. No sorting, no interactivity. Good for small, fixed data that doesn’t need interaction.

df = pd.DataFrame({"Name": ["Alice", "Bob", "Charlie"], "Score": [92, 85, 78]})

st.dataframe(df, use_container_width=True)  # Interactive — sortable, scrollable
st.table(df)                                 # Static — simple display

Metrics: KPI Dashboard Cards

st.metric() displays a label, value, and delta (change indicator):
st.metric("Revenue", "$45,678", "+12%")          # Green delta (positive is good)
st.metric("Bugs", "23", "-5", delta_color="inverse") # Green delta because FEWER bugs is good
st.metric("Users", "1,234", "0")                  # Gray delta (no change)

The delta_color="inverse" parameter flips the color logic — negative deltas show green and positive show red. Use this for metrics where decreasing is good (bugs, costs, response times).
Caching: Don’t Re-Fetch on Every Re-Run

Remember: every widget interaction triggers a re-run. If your script fetches data from an API or database, that fetch happens on every single re-run. For a function that takes 3 seconds, every button click means a 3-second wait.

@st.cache_data solves this:
@st.cache_data(ttl=300)  # Cache for 300 seconds (5 minutes)
def fetch_users():
    response = requests.get("<https://jsonplaceholder.typicode.com/users>")
    return response.json()

users = fetch_users()  # First call: fetches from API. Subsequent calls: uses cache.

The Chat History Pattern

Here’s why session state is essential. Streamlit re-runs the entire script on every interaction. When the user sends a message, the script re-runs, and all previously displayed messages vanish unless you explicitly re-render them.

The solution: store all messages in session state and re-render them on every run:
# Initialize chat history
if "messages" not in st.session_state:
    st.session_state["messages"] = []

# Re-render ALL previous messages on every run
for message in st.session_state["messages"]:
    with st.chat_message(message["role"]):  # "user" or "assistant"
        st.write(message["content"])

# Handle new user input
if prompt := st.chat_input("Ask me anything..."):  # := is the walrus operator
    # Add user message to history
    st.session_state["messages"].append({"role": "user", "content": prompt})
    with st.chat_message("user"):
        st.write(prompt)

    # Get AI response and add to history
    response = get_ai_response(prompt)
    st.session_state["messages"].append({"role": "assistant", "content": response})
    with st.chat_message("assistant"):
        st.write(response)

The := is Python’s walrus operator - it assigns the value of st.chat_input() to prompt and simultaneously checks if it’s truthy (not None or empty). It’s equivalent to:
prompt = st.chat_input("Ask me anything...")
if prompt:
    ...

Linked Lists: A Chain of Connected Nodes

Imagine a scavenger hunt. You get a first clue that says “Go to the library.” At the library, you find a note that says “The secret word is PYTHON. Next clue: go to the park.” At the park: “The secret word is DATA. Next clue: go to the coffee shop.” And so on.

Each stop has two things: some content (the secret word) and a pointer to the next stop (where to go next). You can only follow the chain forward, you can’t jump to the 5th stop without visiting stops 1 through 4 first.

This is exactly how a linked list works. Each element (called a node) stores a value and a reference (pointer) to the next node.

Stacks: Last In, First Out (LIFO)

Think of a stack of plates at a buffet. You can only add a plate to the top, and you can only take a plate from the top.

A stack follows the same rule: the last item added is the first one removed. This is called LIFO, Last In, First Out.

The two core operations:

    Push: Add an item to the top of the stack
    Pop: Remove and return the item from the top of the stack

Where stacks appear in the real world:

    Your browser’s back button - Each page you visit is pushed onto the stack. Click “back” and the most recent page is popped off.
    Undo/redo in text editors - Each action is pushed onto an undo stack. Ctrl+Z pops the most recent action.
    Python’s function call stack - When function A calls function B, which calls function C, Python uses a stack to track where to return.

Queues: First In, First Out (FIFO)

Think of a line at a grocery store. The first person in line is the first person served. New people join at the back.

A queue follows the same rule: the first item added is the first one removed. This is called FIFO, First In, First Out.

The two core operations:

    Enqueue: Add an item to the back of the queue

You’ve already used object-oriented programming in this course, even if you didn’t realize it. The LinkedList and Node classes in the last lesson? That was OOP. Every time you’ve used my_list.append() or my_dict.keys(), you’ve been calling methods on objects. Now we’ll understand the system behind all of it.

Object-oriented programming is a way of organizing code around objects, bundles that combine data and the functions that operate on that data.
Classes and Objects: The Core Idea

A class is a blueprint. An object is something built from that blueprint.

Think of a cookie cutter and cookies. The cookie cutter (class) defines the shape. Each cookie (object) is a specific instance created from that cutter.

In Python:
class Student:
    """Blueprint for a student."""

    def __init__(self, name, grade):
        # These are attributes — data that belongs to each student
        self.name = name
        self.grade = grade

    def is_passing(self):
        # This is a method — a function that belongs to the class
        return self.grade >= 60

    def __repr__(self):
        # This controls how the object looks when printed
        return f"Student(name='{self.name}', grade={self.grade})"

# Creating objects (instances) from the class
alice = Student("Alice", 92)
bob = Student("Bob", 55)

print(alice)              # Student(name='Alice', grade=92)
print(alice.name)         # "Alice" — accessing an attribute
print(alice.is_passing()) # True — calling a method
print(bob.is_passing())   # False

Let’s unpack the key pieces:

__init__ is the constructor a special method that runs automatically when you create a new object. It sets up the object’s initial data.

self is Python’s way of referring to the specific object. When alice.is_passing() is called, self inside the method refers to the alice object.

Attributes (self.name, self.grade) are the data each object carries.

Methods (is_passing()) are functions that belong to the class. They can access and modify the object’s attributes through self.
Why OOP? Organizing Complexity

Without OOP:
alice_name = "Alice"
alice_grade = 92
bob_name = "Bob"
bob_grade = 55

def is_passing(grade):
    return grade >= 60

This works for two students. But what about 500? You’d have 1,000 variables.

With OOP:
students = [
    Student("Alice", 92),
    Student("Bob", 55),
    Student("Charlie", 78),
]

failing = [s for s in students if not s.is_passing()]

The data and behavior are bundled together. Clean, scalable, maintainable.


Inheritance: Building on What Exists

Sometimes you need a specialized version of a class. Rather than writing from scratch, you inherit from an existing class.
class Person:
    """Base class for any person."""

    def __init__(self, name, email):
        self.name = name
        self.email = email

    def introduce(self):
        return f"Hi, I'm {self.name}."

class Student(Person):
    """A student is a person with a grade."""

    def __init__(self, name, email, grade):
        super().__init__(name, email)  # Call the parent's __init__
        self.grade = grade             # Add student-specific data

    def is_passing(self):
        return self.grade >= 60

    def introduce(self):
        base = super().introduce()
        status = "passing" if self.is_passing() else "needs support"
        return f"{base} I'm a student, currently {status}."

class Instructor(Person):
    """An instructor is a person with a course."""

    def __init__(self, name, email, course):
        super().__init__(name, email)
        self.course = course

    def introduce(self):
        base = super().introduce()
        return f"{base} I teach {self.course}."

alice = Student("Alice", "alice@school.com", 92)
prof = Instructor("Dr. Smith", "smith@school.com", "AI Foundations")

print(alice.introduce())
# Hi, I'm Alice. I'm a student, currently passing.

print(prof.introduce())
# Hi, I'm Dr. Smith. I teach AI Foundations.

What’s happening:

    Person is the parent class. It defines what every person has.
    Student and Instructor are child classes. They inherit from Person but add their own attributes and override introduce().
    super().__init__(name, email) calls the parent’s constructor so you don’t repeat setup code.

When NOT to Use OOP

OOP is a tool, not a religion. Sometimes it adds unnecessary complexity:

Simple scripts - Quick data-cleaning script that runs once? Functions are fine.

Stateless operations - If a function doesn’t need to remember anything between calls, it doesn’t need to be a method.

Data-only structures - Just bundling data? Consider a dictionary or dataclass instead.

A good rule of thumb: use OOP when you have data and behavior that belong together, especially when you’ll create multiple instances or need to build specialized versions through inheritance.
